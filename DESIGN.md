# work-brain — system design

**rev 2 (final) · 2026-07-05 · supersedes `DESIGN.html` (rev 1)**

---

## 1. What this is

A work-only second brain: a private, git-backed Obsidian vault that ingests my
work exhaust (meetings, Linear tickets, Slack, email, dictated brain-dumps)
automatically, and serves it back — to me and to AI agents — as current,
token-efficient context.

Rev 1 described the wiring but not the point. The point, in priority order:

1. **Working memory for me.** When a topic resurfaces or a meeting starts, I
   recover the full thread — what was decided, who said what, what's still
   open — in under a minute, instead of reconstructing it from scrollback and
   memory.
2. **Context substrate for AI agents.** Agents (Claude Code today; claude.ai
   web/mobile via MCP later) read the brain instead of me re-explaining my
   work. Delegation stops paying a context tax.
3. **Documentation hub and portfolio view.** The vault is the source of truth
   for *how what I've built works* and *where everything stands*. Each project
   note documents the project and links out to the code repos that hold full
   depth (hub-and-spoke). A dashboard note answers "what's in progress, what's
   outstanding, what ideas are queued" at a glance.

A durable record of shipped work and received feedback (useful at review time)
falls out of this as a side effect; it is not the design driver.

### Success tests (~3 months in)

| Test | Pass condition |
|---|---|
| **Zero re-explain** | Any agent can answer "what's the current state of X, what was decided, what's open" accurately without me pasting context. |
| **Cold recall** | Full thread recovered in < 1 minute of querying, before any meeting or when a stale topic returns. |
| **Portfolio clarity** | Outstanding tasks, in-progress projects, and future ideas are visible in one dashboard view. |
| **Docs hub** | Every project has a "how it works" path: vault note → linked repos for depth. |

## 2. Core constraints

- **The private GitHub repo is the single source of truth.** Every component —
  CI syncs, the MCP service, local edits — converges on it. Nothing holds
  state that isn't in (or derivable from) the repo. No second store, ever.
- **Plain markdown, Obsidian-compatible.** Human hand-editing in Obsidian is a
  first-class, always-available path alongside automation.
- **Agent-first retrieval.** Retrieval quality comes from *structure*
  (`AGENTS.md`, strict frontmatter, wikilinks, stable slugs, maintained
  digests), not embeddings. Semantic-search plugins (Smart Connections) are
  optional human conveniences, not load-bearing.
- **Employer-sanctioned.** This is cleared with security/IT as sanctioned
  personal tooling. Data lives only in the private repo; LLM processing goes
  through the Anthropic API (no-training terms). No colleague data to consumer
  SaaS memory products.

## 4. The vault

```
work-brain/
├─ AGENTS.md         how agents should read/write this vault: layout, conventions,
│                    where digests live, what they may edit. THE agent entry point.
├─ DASHBOARD.md      auto-maintained portfolio view: projects by status,
│                    open actions count, ideas queue. Regenerated by every sync.
├─ 00-inbox/         actions.md (todos + source msg ids) · transcripts/ · braindumps/
├─ 01-daily/         daily notes; brain-dumps default here
├─ 02-projects/<slug>/
│    _project.md     frontmatter: status, repos: [links to code repos], people.
│                    Body: ## Current state (THE DIGEST — see §6) ·
│                    ## How it works (docs hub; deep detail lives in the repos) ·
│                    ## Decisions · ## Ideas / future
│    tasks/          one note per Linear issue
│    done.md         completed-work log
├─ 03-meetings/      cleaned, wiki-linked notes · _raw/ originals
├─ 04-people/        one note per colleague
├─ 05-feedback/      positive + critical, from Slack + email
├─ 06-interactions/  weekly Slack digests
├─ 07-reference/     durable docs · ideas not yet attached to a project
├─ 99-meta/          sync-state.json (cursors + dedup) · actions-done.md
├─ scripts/          syncs, ingest, router, hooks + lib/
├─ webhook/          the always-on vault service (receiver + MCP, §7)
└─ .github/ .claude/ CI workflows · hooks + /braindump command
```

**Conventions (specified in `AGENTS.md`, enforced by `lib/vault.py`):**
frontmatter on every note (`type`, `date`, `project`, `people`, `source`);
wikilinks for every person/project mention; kebab-case slugs that never change;
automation writes append-only into machine-owned paths.

## 5. Writers and the write topology

Three writers share the repo. Convergence is designed, not remembered:

| Writer | When | How it stays safe |
|---|---|---|
| **Me, in Obsidian** | ad hoc | **obsidian-git** plugin: auto-pull on open, auto-commit+push on ~10 min interval. Manual push is a backstop, not the mechanism. |
| **Claude Code, locally** | end of any turn that touched the vault | **Stop/SessionEnd hook** (`scripts/session_capture.py`): one batched `git add -A → commit → pull --rebase → push` as the last step of the agent cycle. Never per-file commits. |
| **Automation** (CI syncs, webhook receiver, MCP writes) | scheduled / per event / per call | always `pull --rebase` before push, retry once on rejection. Appends only to machine-owned paths: `00-inbox/`, `02-projects/*/tasks/`, `03-meetings/_raw/`, `06-interactions/`, `99-meta/`, plus the digest/dashboard sections it owns. |

The ownership rule makes same-line collisions structurally rare; because
automation appends, git merges the rest.

## 6. The digest invariant

**Every writer leaves the digest current.** Each project's `_project.md` has a
`## Current state` section (status, recent decisions, open threads, links
deeper). Whichever component writes to a project — Linear sync, transcript
ingest, braindump router, an MCP write — also refreshes that section (and
`DASHBOARD.md`) in the same commit.

Consequence: answering "where is project X?" costs a single ~500-token file
read — no query-time LLM, no latency. Summarization is paid once at write time
(writes are rare; reads are frequent). The digest doubles as the
human-readable project summary in Obsidian.

## 7. The remote MCP: vault service on git

The always-on webhook receiver grows into a small **vault service** — the one
deployed component. It is a *port onto the repo*, never a second store:

- keeps a shallow clone; `pull` before every read; every write is a
  `commit + push` (rebase-retry on conflict).
- **Purpose-shaped tools**, not generic file CRUD — this is what makes agent
  access token-efficient:
  - `get_project_context(slug)` → the maintained digest + frontmatter + recent activity, token-budgeted
  - `get_dashboard()` → portfolio view
  - `search(query, type?)` → ranked note excerpts, not whole files
  - `read_note(path)` → full note when the agent asks for depth
  - `append_note(path, content)` / `add_action(text, source)` / `log_braindump(text)` → writes, each refreshing the affected digest
- **Auth:** static bearer token first (Claude Code, CLI agents). Built on a
  framework with pluggable auth (e.g. FastMCP) so **OAuth 2.1** is an upgrade,
  not a rewrite — that unlocks claude.ai web/mobile as a custom connector.
- Rejected alternatives: GitHub-API passthrough (weak search, token cost lands
  on the agent), separate index store (drift risk, violates single source of
  truth), adopting basic-memory (generic notes-CRUD tool shapes; we'd still
  build ingestion and remote hosting ourselves — kept as a reference).

## 8. Ingestion pipelines

| Source | Cadence | Mechanism |
|---|---|---|
| **Fathom** (confirmed: covers all meetings) | per meeting | webhook → vault service verifies signature, normalizes via adapter, commits raw to `00-inbox/transcripts/` → push-triggered Action runs `ingest_transcript.py`: Claude produces summary/decisions/actions, writes a wiki-linked note in `03-meetings/`, files actions, refreshes digests |
| **Linear** | weekly cron (GitHub Actions) | `sync_linear.py`: issues I own/follow that changed; one note per issue under the project; completed → `done.md`; digest refresh |
| **Slack** | weekly cron | `sync_slack.py` (user token, search-based — the no-admin path): sent / @-mentions / DMs → weekly digest in `06-interactions/`; feedback flagged; keyword hits → `00-inbox/actions.md` with embedded `channel`+`ts` |
| **Gmail** | weekly cron | `sync_email.py` (read-only): feedback-shaped threads → `05-feedback/` |
| **Dictation** | on demand | `/braindump` in Claude Code → `braindump_router.py`: Claude splits and files each piece to project / person / feedback / daily / inbox |

**Action loop (Phase 3):** actions carry their Slack `channel`+`ts`; ticking a
box makes `close_actions.py` react ✅ on the source message and archive the
line to `99-meta/actions-done.md`.

## 9. Phasing — context first

| Phase | Ships | Why this order |
|---|---|---|
| **P1 — the substrate** | vault + `AGENTS.md` + conventions · Fathom webhook→ingest pipeline · Linear sync · rolling digests + `DASHBOARD.md` · end-of-turn push hook + obsidian-git · `/braindump` | Meetings + Linear are the richest context. After P1, any agent with a clone of the repo passes the zero-re-explain test locally. |
| **P2 — the port** | vault service MCP: read/search/digest/write tools, bearer auth | Makes the substrate remotely accessible and cheap. Not blocking P1 — local clones work day 1. |
| **P3 — the loop** | Slack + email syncs · action inbox with ✅ close-the-loop · OAuth 2.1 (claude.ai/mobile) | Highest plumbing cost, serves the lowest-ranked job (action reliability); lands once the substrate has proven itself. |

## 11. Decision log

| Decision | Chosen | Rejected & why |
|---|---|---|
| Primary job | context recall + agent substrate (+ docs hub/portfolio) | perf-record-first (falls out anyway); action-reliability-first (deferred to P3) |
| Retrieval | structure-first, `AGENTS.md`, Claude-first | embeddings-first (does nothing for agents; grep + structure suffices; revisit only if recall demonstrably fails) |
| Source of truth | the private GitHub repo, alone | MCP with own DB syncing to git "eventually" (two sources of truth) |
| MCP backend | vault service on a git clone | GitHub API passthrough (weak search); index+git dual store (drift); basic-memory (generic tools, dependency) |
| Digests | maintained at write time by every writer | query-time summarization (per-call LLM cost × agent call frequency); raw slices (token cost on every consumer) |
| Local convergence | obsidian-git auto-sync + batched end-of-turn hook | "remember to push" (a hope, not a mechanism); MCP-only writes (kills frictionless hand-editing) |
| Auth | bearer now, OAuth 2.1 next | OAuth day one (delays shipping); bearer forever (locks out claude.ai/mobile) |
| Slack coverage | search-based, user token | Enterprise Grid Discovery firehose (admin-only) |
| Build vs buy | build (scaffold exists) | surveyed Jul 2026: no tool covers ingestion (Slack/Gmail/Linear/meetings → markdown) or the ✅ close-loop; memory-infra tools (mem0, Zep, basic-memory, …) are stores, not pipelines |

## 13. Risks & open items

- **Vault service hosting** — Render / Fly / Railway; pick at P2 start. The
  single always-on component; everything else degrades gracefully without it
  (transcripts queue at Fathom, syncs are cron).
- **Digest drift** — if a writer skips the digest refresh, the invariant rots
  silently. Mitigation: refresh lives in `lib/vault.py` so every writer gets
  it for free; a weekly CI step lints digest `updated:` stamps vs latest
  activity.
- **Windows local hooks** — end-of-turn hook must work under PowerShell/Git
  Bash on Windows; test early in P1.
- **Slack keyword tuning** — the action-inbox signal/noise depends on keyword
  lists in `config.yaml`; expect iteration in P3.
